# Exo Launcher architecture

See the [architecture overview and page index](docs/architecture/README.md) for a runtime diagram and further reading.

Exo is a WinUI 3 host (.NET 10, Windows App SDK 2) with one WebView2 running React 19 (`ui/`). `ExoLauncher/MainWindow.xaml.cs` creates the host; `ui/src/components/LauncherApp.tsx` places every room through `Room` (`ui/src/components/shell/BootGate.tsx`). Behind the splash each room is warmed and laid out out of sight (`is-backstage` in `ui/src/exo-shell.css`: fixed at its own size under the Bar, hidden, inert, strictly contained), so a first visit costs what a later one does; reads stay tied to the room on screen.

The frontend uses its own controls (`ui/src/components/ui/`: `Button`, `Menu`, `Slider`, `Qr`; `ui/src/components/Switch.tsx`), its own icons through `ui/src/brand/icons.tsx` (DESIGN.md › Icons) and Tailwind 4. Styles are one file per room or surface in `ui/src/styles/`, imported in order by `ui/src/tokens.css`, then `ui/src/exo-shell.css`, `styles/rooms.css` and `styles/hosted-room.css` from `main.tsx`. The three Appearances are `<html data-exo-theme>` (DESIGN.md › Tokens).

React calls typed methods in `ui/src/lib/host.ts`; `Services/WebHostBridge*.cs` dispatches them to native services. Store adapters own official-client launch, ownership, installation and updates. Secrets stay in native stores.

- WebView2 (`Helpers/WebViewEnvironmentFactory`, user-data folder `webview`, `webview-debug` in Debug): the shell and the music web players share one environment, so one browser, GPU and network process; GOG and Epic sign-in (`Services/StoreAuthWindow`) make short-lived environments of their own. The shell runs on the Default profile at `app.exo-launcher.local` with web messages and no host objects, plus its own `*.exo-launcher.local` hosts (covers, thumbnails, Exo Mouse, payments, captures). The YouTube Music and Apple Music players run on the named `embedded` profile with none of those, and its extensions (Exo Shield, SponsorBlock; `Helpers/WebExtensions`, each pinned to the hash of its folder) live only there. Never give an embedded view a host object or virtual host, and never attach an extension to the shell.
- Start (`MainWindow.PrepareConnectedRoomsAsync`, `shell.prepare`, once the library is usable and onboarding is done, again on every shell load): Exo's Discord session connects and Exo Capture starts (Exo Shaders' engine doesn't: see Shaders). The chosen music service's page starts hidden with its room, which is preloaded behind the splash. An idle music player suspends, then closes after 15 minutes asleep (`MusicReleaseDelay`). Steam is never started to check ownership (`Adapters/SteamClientReady`). `tools/measure-memory.ps1` prints the process tree's memory; the design target is one process per Chromium role.
- Background behavior (`MainWindow.TrimLoopAsync`, `Helpers/BackgroundTrim`, `Helpers/ForegroundWatcher`, `Helpers/ManagedProcessResources`): "in front" means the foreground window belongs to Exo's process (an `EVENT_SYSTEM_FOREGROUND` hook compares the foreground window's root owner with Exo's; `Window.Activated` is unreliable with a foreign top-level HWND). Managed scope is explicit: one cohort per root (Exo, Exo's WebView2 environment and each store client's UI helpers), walked with start-time checks so a reused parent pid never pulls in an unrelated process or Exo itself. The loop ticks every 5 s while Exo is behind, a hidden embedded renderer exists or a change is settling (15 s), and every 30 s otherwise.
  - While Exo is not in front, managed processes get low memory priority (not Exo's host during a call) and the host enters efficiency mode. Hidden embedded renderers have their working set emptied, again only after 32 MB of growth (`ManagedProcessPolicyState.RetrimGrowthBytes`) and at most every 30 s. Exo's own host and shell lose their working set only while its window is minimized or hidden.
  - A hidden web player suspends after 60 s silent; music is never suspended while playing.
  - Store clients' UI helpers (`Adapters/StoreClientHelpers`: steamwebhelper, EpicWebHelper or WebView2 under EpicGamesLauncher, QtWebEngineProcess under EADesktop, UplayWebCore under upc or UbisoftConnect, GalaxyClient Helper, Battle.net's `--type=` renderers; each a start-time-checked child chain of the client's root, so nothing a game started can join): while the client has no main window on screen, is not in an Exo handoff and was not just opened by the user or a sign-in, they get low memory priority and an emptied working set (after 32 MB of growth, at most every 5 minutes, since the Steam overlay draws in steamwebhelper). No EcoQoS or priority class, nothing closed or suspended, never the client's main process or services, and Riot is not in the list.
  - Nothing on screen is trimmed, no process outside the cohorts is touched, and everything is restored on return. `MainWindow.Resources` sums the cohorts for a `Trim:` line in app.log every 5 minutes.
- Discord is Exo's own client (`Services/DiscordClient`, `discord.*`; `docs/architecture/discord-client.md`): the host holds the session, REST, gateway and voice, and the page draws the room. Its unread count reaches the Bar's tab and the taskbar button through `friends.badge`. Exo never hosts, installs or patches the Discord desktop app (it can uninstall it, `Services/ReplacedApps`).
- Hosted pages are always optimized; there is no setting, and an older Exo's `appOptimizations` and `discordEquicord` keys in `settings.json` are ignored. YouTube Music and Apple Music: `Helpers/EmbeddedClientPresentation` marks the page, hides upsells and skips a hidden page's layout and paint (`content-visibility`).
- Music is Exo's own player for Spotify, YouTube Music and Apple Music (`ui/src/components/music/`: `NativeMusicRoom` runs the engine's lifecycle, `MusicPlayer` draws library, home, search, pages, panels and the player strip; `docs/architecture/music-engines.md`). Each service plugs in through an adapter in `ui/src/lib/musicAdapters.ts` answering the same shapes (`ui/src/lib/player.ts`); Jam, Friend activity and Devices show only for a service that has them. The service runs hidden as the engine; Exo never reads a token, plays or decodes audio, or changes what the account may do.
  - Spotify (`spotify.start` / `view` / `act` / `link`, `MainWindow.SpotifyRoom`): open.spotify.com loads hidden (transparent, no input) on the embedded profile, and sign-in opens Spotify's own page in Exo's window. Exo never starts, hosts, installs or prompts for the Spotify desktop app; one the user runs is left alone. `Helpers/SpotifyNative` evaluates one adapter in the page through WebView2's DevTools protocol: Spotify 1.3's platform APIs are a registry keyed by `Symbol.for(name)` (PlayerAPI, LibraryAPI, PlaylistAPI, ShowAPI, ConnectAPI, ConnectDevicesAPI, SocialConnectAPI for Jam, BuddyFeedAPI for Friend activity, RecentlyPlayedAPI, RequestBuilder), found through the React tree; catalog pages go through the client's own GraphQL with this build's persisted-query hashes (the page finds them in the module factories it has registered), lyrics through RequestBuilder to color-lyrics. Answers are shaped in the page into small DTOs; the host only validates URIs and ids. A Jam's join token stays in the page; only its share link leaves it.
  - YouTube Music (`ytmusic.start` / `view` / `act`, `MainWindow.WebMusicRoom`): music.youtube.com loads hidden (transparent, no input) and `Helpers/YouTubeMusicNative` evaluates in it through WebView2's DevTools protocol: pages from its own InnerTube client (/browse, /search, /next, /like), playing and skipping through its `yt-navigate` event, shuffle and repeat through its player bar, queue and like state from its store. Ids cross as `ytm:<kind>:<id>`.
  - Apple Music (`applemusic.start` / `view` / `act`, the same `WebMusicRoom`): its Windows app is native WinUI/C++ with nothing to drive without UI automation, so the engine is music.apple.com (opened on its search page), driven by `Helpers/AppleMusicNative` through the page's own `MusicKit.getInstance()`: Home, recently played, catalog, library, lyrics, favorites and playlist edits through the same `api.music` calls the page's menus send, with its developer token and the user's sign-in, which Exo never reads; play and transport run as the user's click (`userGesture`). Playback and its DRM stay inside Apple's page. Ids cross as `am:<type>:<id>`. A saved Cider choice reads as Apple Music (`WebClientPreferences`).
  - Switching providers closes the previous page. Leaving Music for another room only hides it.
  - The mini player: `Services/MediaSessionService` reads the song from the provider's page (`MusicNowPlaying`) and sends transport to the same page; Windows' media sessions are read only for what another app plays, for your call (`OtherMusicAsync`). Volume is the page's own (`Services/MusicAppVolume`: Spotify's PlaybackAPI, YouTube Music's player element, Apple Music's `MusicKit.getInstance().volume`), long-polled into `music.volume`; the first answer folds the Windows session volume (`Services/AppVolume`) into it.
- Devices is Exo Mouse, a separate program in `mouse/` (AGPL-3.0-or-later, `mouse/LICENSE`) built on `@openmouse/protocol` (AGPL-3.0, pinned 0.48.1). Exo Launcher is not covered by the AGPL; the two meet only through postMessage. The `ui` build runs `npm --prefix ../mouse run build` into `ExoLauncher/wwwroot/mouse`, and `DevicesRoom.tsx` frames it on its own origin, `https://mouse.exo-launcher.local` (`.exo-devices-frame`), filling the room.
  - The relay (`ui/src/lib/mouseRelay.ts`, installed once with Exo and never removed, so the module works while the room is hidden) answers only `hid.list`, `hid.open`, `hid.close`, `hid.sendReport`, `hid.sendFeatureReport`, `hid.receiveFeatureReport`, `hid.receiveInputReport`, `exo.games` (installed games by id, title and cached cover thumbnail, for game-linked profiles), `exo.profiles.read` / `write` (`mouse.profiles.get` / `set`, `mouse\profiles.json` under Exo's data folder, at most 512 KB), `exo.textScale`, `exo.motion`, `exo.theme` and `exo.mouseCore` (the CPU core panel: `system.mouseCore` with no action or with `measure`, `apply` or `undo`, anything else refused before the host; the host keeps the device, the CPU it offers and the backup, and Windows asks before a change). It takes one-way notices, battery state (Exo status lines and the Bar's mouse capsule) and the active profile's name, and posts only `hid.input`, `hid.changed`, `game.runState` (id, `isRunning`), `exo.textScale`, `exo.motion` and `exo.theme`; `DevicesRoom.tsx` posts `room.visible`. Messages from anywhere but that frame, and every other method, are ignored.
  - Native HID is `Services/Hid/HidService` (+ `HidInterop`) behind `WebHostBridge.Hid`: devices listed as WebHID does (collections grouped by their USB interface, so two identical mice stay separate), every collection opened shared, never exclusive (which would freeze the mouse's own input); of the collections Windows keeps, keyboards are skipped and a mouse collection is opened with no access, for feature reports only. Input reports are read from open, Chromium's byte conventions matched, a blocked control transfer abandoned after 3 s, arrivals and removals announced through `CM_Register_Notification`. Devices are named by an opaque hashed key; no device path reaches the page. No vendor software, bridge or driver install.
  - `mouse/scripts/patch-protocol.mjs` runs before each build and stops it when the library version changes. It teaches the library the Finalmouse Starlight X (the receiver light's TMR-DS mode 4 and custom color, command 54; command 53 actuation; the cabled 361d:0310/0311; battery 255 on command 38).
  - `Services/MouseBridgeRetirement` runs once for users of the retired OpenMouse Bridge mode (`settings.json` `mouseBridge: "exo"`): Exo's `openmouse-bridge.json` profiles go into the app's `config.json` (never while it runs), then the settings are cleared. The app is not started and its sign-in entry is not put back.
  - Device pictures (`devices.image`, `Services/DeviceImages`): `ExoLauncher/Assets/device-images.json` lists one official product picture per model and variant (links only; the pictures are their makers' and never ship). A request resolves by devices.list's model id (a mouse by the OpenMouse render Exo Mouse picked for it) and color or layout, else by the longest model name its maker and name contain; the picture is fetched once from an approved host (the `DevicePictures` row of `NetworkDestinations`, every redirect hop checked, 8 MB cap, PNG/JPEG/WebP by signature), cut from a white or flat light studio background as a soft matte, as tight as the background is flat so white and clear shells stay (per entry `cut`: the studio shadow or floor reflection, holes in cable loops and headbands), fitted never larger than 1:1 into a transparent 1200×800 frame with an 8% margin, and kept as `device-images\v<look>-<hash>.png`, served at `devices.exo-launcher.local`.
- Store (`Services/StoreService*.cs`, `store.*`) reads only public, anonymous storefront endpoints and caches each answer under `store`. Home: Steam's IStoreQueryService/Query (top sellers, coming soon, on sale with `price_filters.min_discount_percent`), and the most-wishlisted list, saved as `home-v5.json`; each answer is then made for this person on the PC (`StoreService.ForYou.cs`): owned games (by Steam app id or title) leave it, and a taste from the library's hours (any store: a Steam game by app id, another found on Steam by exact title or from a short built-in tag list for big games not on Steam) and the wishlist adds Picked for you and Because you play shelves from tag-filtered Query lists (kept 30 minutes) and orders the banner; the Calendar uses the same taste. Card facts come from IStoreBrowseService/GetItems in batches of 50 into `items-v2.json` (fresh 12 hours, kept two weeks); tag names from IStoreService/GetTagList into `tags-v1.json` for a week. `store.game` answers from appdetails (4 s, then one 8 s retry) plus GetItems (3 s cap), deduplicates concurrent asks (hover warm-up, then click) and caches 20 minutes; `store.gameOffers` adds CheapShark's official-store rows and, in the US, the lowest price it has seen (`games?id=`, under the same 429 pause); `store.gameReviews` adds Steam's Recent reviews (IUserReviewsService/GetAppReviews, 3 s), asked only once a page opens, never to warm one. Epic's GraphQL is not used: it sits behind Cloudflare bot protection, and Exo does not work around that. PC requirements are read out of Steam's HTML (`StoreService.Specs.cs`) and judged against this PC at answer time (`StoreService.Fit.cs`, `Helpers/SystemSpecs.cs`: processor, graphics card, memory and Windows read once, free space on the roomiest Steam library drive each time), each part on one rough performance scale per kind, compared with the same maker's part when the game names one. Search caches 5 minutes per query and a newer query cancels the one in flight. `store.changed` carries `what` (`home` or `wishlist`) so the room reloads only that part. PERF lines in app.log time each source.
- Covers: `Services/CoverArtService` caches art under `covers\`, which the shell reads at `covers.exo-launcher.local/<token>/` through `Helpers/LocalFileHost` (this run's token in every address, other pages refused, kept by the browser for the run). Exo stores and compares cover addresses without the token; `WebHostBridge.ToPage` adds it to everything the bridge sends and `FromPage` takes it out of requests, and the page learns the base for the cache files it names itself from `art.base`. Small art (grid cards, folders, captures, Shaders, Upscalers, Exo Mouse's games) asks `thumbs.exo-launcher.local/<token>/<cover file>?w=<px>` (`ui/src/lib/coverThumb.ts`): `MainWindow.ReadThumbnailAsync`, on the same host class, defers to `CoverArtService.ReadThumbnailAsync` (`CoverArtService.Thumbnails.cs`), which decodes the JPEG with Windows.Graphics.Imaging (EXIF-oriented, sRGB), scales it with its own Lanczos-3 pass (Fant first only above 4096×4096), stores `thumb-<w>-<stamp>-<cover>.jpg` beside it (stamp: a hash of the source's length, write time and the thumbnail format, so a replaced cover gets a new thumbnail and the old one is deleted), and serves the original when it is PNG/GIF/WebP or the thumbnail would be within a quarter of it. `w` is twice the widest card the screen can produce in device pixels, in 120 px steps from 240; it only grows within a session, and above 720 the original is used. The game sheet's cover loads the full file and shows the card's bitmap until it decodes.
- Achievements are read natively per store (`Services/AchievementService`) after a launched game exits and when a game's sheet opens with missing or stale counts. Steam reads `librarycache/achievement_progress.json` and the per-game librarycache file, and the Web API alongside when a key is stored. The counts stay on this PC; the sheet shows them (`game.extras`, `game.achievements`). There are no unlock pop-ups.
- Shaders: PC › Graphics › Shaders is Exo Shaders, Exo's own shader add-on (Exo's GPL-3.0 fork of SCSKiller 1.4.6, a separate program in `shaders/` that Exo runs as its own process, never compiled into Exo; `shaders/UPSTREAM.md`; each release's source at getexo.app/source): a headless engine (`Services/ShadersAddon`, NDJSON over stdio) driven by Exo's own page (`ui/src/components/shaders/ShadersBoard.tsx`, `shaders.addon` / `shaders.call`, `MainWindow.Shaders`). Without the add-on the tab says Exo Shaders is not installed. The engine starts when Compile or Refresh is pressed on the board (`ShadersAddon.StartMethods`: `game.compile`, `queue.add`, `queue.start`, `queue.resume`, `scan`), and for Exo's own rebuild (`Services/ShaderRebuild`, `ShaderRebuildWatch`) while nobody uses the PC (`Helpers/PcIdle`): after a driver change it queues every game compiled for another driver; with nothing queued, an install, uninstall or update since the engine's last scan (`ScsKillerStatus.Installed`: each installed game's id, folder, size and Steam build) has it `scan`, and every game the engine lists as ready (never compiled) or stale (updated or wiped) is queued (`ScsKillerStatus.ToCompile`), most played first; a game that doesn't compile after three starts is left until the driver changes (`shader-rebuild.json`'s `GaveUp`). Nothing else starts it (not the board opening, a game exiting or the time of day), and it exits by itself 15 seconds after its last scan, compile and the passes after them end (its `exitWhenIdle`; the board being on screen doesn't keep it). While it runs, Exo sends it the installed games (`exo.library`), each marked `noRecorder` where Exo keeps the recorder out (`ShadersAddon.KeepsRecorderOut`: Exo's anti-cheat answer refuses it, or a Steam game set to start without its anti-cheat, which gets it only for an Exo session through `recorder.set {session: true}`), so its "Record games" never puts one there by itself. A press that meets an engine on its way out (its `exiting` event) waits for it and starts the next. Without it, `shaders.addon` and the board's `snapshot` return the state it left when it last exited (`exo-snapshot.json` in its data folder, rev 0, no queue), and `ui.visible`, `queue.move`, `queue.remove`, `queue.pause` and `queue.stop` are answered without it; the board goes back to that state when the engine exits. The engine's own settings policy compiles nothing by itself (Exo's rebuild above does) and keeps no AMD cache aside (one kept by an earlier version goes back into the driver's cache at its next run); its "when idle" work (plan checks, precompiled databases) runs only inside a run you started and only while the PC is really idle: ten minutes without input (one while locked or with the display off), nothing full screen, no sound or microphone in use, other programs under 15% of the processor over the last minute, no game, not on battery (the engine's own copy of `Helpers/PcIdle`, which also gates Exo's game and chipset updates while you're away). `Services/ScsKillerStatus` answers `shaders.estimates` (each game's compile time on this PC from the engine's estimate, sized from its shader count where it has none; the board takes the snapshot's own estimate first, learned or rough, and these as rough) and `shaders.status` for a game sheet from the engine's `games.json` and each game's `games\<id>\state.json` (Warmed only for a `WarmedDriverId` whose driver is installed now), watches both to post `shaders.changed`, and once deletes the `tools\scskiller` copy older versions downloaded.
- FPS counter (`Services/FpsCounter.cs`, `fps.counter`; `settings.fpsCounter`, `fpsCounterPosition`, `fpsCounterItems`): off by default. While on and a game runs, `Helpers/PresentTrace.cs` holds one real-time ETW session (`ExoFpsCounter`, its own thread; a stale one left by a crash is stopped by name) on Microsoft-Windows-DXGI (Present 42, PresentMultiplaneOverlay 55), Microsoft-Windows-D3D9 (Present 1) and Microsoft-Windows-DxgKrnl (Blit 166, Flip 168, FlipMultiPlaneOverlay 252, ids from PresentMon's headers and the manifests), asked for by event id. It sends nothing while the game isn't in front (`Run`, and the overlay then has no timer: it waits on a foreground event), DXGI and D3D9 only for the game's own processes (a PID filter at the source), and the kernel's events only for a game that has made no API present in its first 2 s (Vulkan, OpenGL). The callback allocates nothing. `Helpers/FpsWindow.cs` turns the timestamps into a held FPS over the last second and 0 for a stall; 1% low is worked out only when its item is on. The game follows the 5 s run-state poll (`GameProcessRegistry.TreeOf`: the verified process, its folder's programs, what they started, without stores, overlays or anti-cheat), and a game staged by Prepare (`ShaderPrepare.Preparing`) isn't one. Nothing runs without a game. No injection, hook or handle beyond the poll's own. `FpsOverlay.cs` draws it with GDI on a click-through layered window on its own thread, twice a second at most, only on change. Items (`FpsItems`) are read once a second, only while switched on with the game in front: GPU use, temperature and VRAM from Windows' graphics statistics (`Helpers/GpuStats.cs`, D3DKMT, what Task Manager reads, no vendor library), CPU and RAM from `GetSystemTimes` and `GlobalMemoryStatusEx`. There is no CPU temperature: Windows has no plain source for it, and the others need a kernel driver. A session needs administrator rights, Performance Log Users, or its own rights. With UAC off or Exo run as administrator `StartTrace` just works and nothing is asked. Otherwise turning it on gives this user's SID rights on this one session's GUID and the three providers (`PresentTrace.AddRightsCommand`, `EventAccessControl` through `ElevatedCommands`, Windows' one prompt): checked against a SID the token already has, so no new sign-in. If Windows still says access denied, it falls back on Performance Log Users by SID, which waits for a sign-out (`tools/fps-permission-check.ps1` proves the first on a PC whose owner runs it). Exo itself is never elevated.
- Autopilot's telemetry (`Services/AutopilotWatch.cs`, `StutterAnalysis.cs`, `autopilot.state`, event `autopilot.report`; `docs/architecture/autopilot.md`): rides the session recorder's one-second look (`SessionRecorderHost`, the same frames from the same trace, no second session). While a library game is in front `AutopilotSampler` reads, once a second and without rights or a driver, `GetSystemTimes`, `GlobalMemoryStatusEx`, `GpuStats` (use, temperature, video memory against the card's own), Windows' counters through `Helpers/PdhCounters` (standby list, free and zero pages, the busiest processor's % DPC and interrupt time, % Processor Performance, any ACPI thermal zone's passive limit) and the kernel's process list (`Helpers/ProcessSnapshot`: one NtQuerySystemInformation, each process's processor time, writes and hard faults, nothing opened). `StutterAnalyzer` (pure) marks a stutter (over 2.5 times the median of the last 30 seconds' frame time and 8 ms over it) and puts it down to what held that second or the one before. At the session's end (a minute of frames at least) the report goes into `autopilot-reports.json` (this PC only, 50 newest, 90 days) and the page is told; PC › Autopilot shows it. Nothing is said during play and nothing leaves the PC.
- Best settings (`Services/GameSettings`, `game.settings`, the game sheet): Exo's values for this PC written into a game's own settings file when the game page's Optimize line is pressed, in groups that can each be put back. Modern Warfare 4 first (`GameSettings.CallOfDuty`: `%LOCALAPPDATA%\Activision\Call of Duty\players\s.1.0.cod26.txt`, found by the `cod26` folder in the game's install). Only the lines Exo knows change, each to a value the line itself lists (`one of …` or `low to high`), so an update that drops a choice drops that change; duplicate lines all change; the rest stays byte for byte (line breaks, BOM, a read-only flag). Groups come from this PC and the file itself: render threads from the processor's fast cores less one (one CCD on a two-CCD Ryzen; `MouseCore`'s topology), the latency switch from the card's maker, the upscaler and its preset from the card and output resolution the game wrote (`GPUName`, `Resolution`), textures and the video memory budget from the card's memory (`GpuCapability.VideoMemoryGb`). Rocket League (`GameSettings.RocketLeague`, Epic's or Steam's install, found by `TAGame` and `Binaries\Win64\RocketLeague.exe`): both copies read one `Documents\My Games\Rocket League\TAGame\Config\TASystemSettings.ini`, an Unreal Engine 3 ini that `GameSettings.Ini` reads (only the profile's keys inside `[SystemSettings]`, the live section, each allowed what Exo knows the engine takes; bytes read one to one as Latin-1, booleans written in the line's own casing); the menu's own choices live in the account's encrypted `.save` and are never written. Phantom Blade Zero (`GameSettings.PhantomBlade`, any store's install, found by its `ProjectPBZ` project folder; its program is `platform\{store}\PBZ.exe`, the top `PBZ.exe` being the store's launcher): `%LOCALAPPDATA%\ProjectPBZ\Saved\Config\Windows\GameUserSettings.ini`, Unreal Engine 5's, read by `GameSettings.Ini` with the settings class's section `[/Script/ProjectPBZ.PBZSettingsLocal]` as the live one, and only its window mode lines written; the Video page is JSON in GCM-sealed saves in the install's `ProjectPBZ\Saved` (`PBZLocalSetting.sav`, `PBZSharedSetting.sav`) that the game authenticates as it loads, and the ini's `[GraphicsQualitySettings]` and `[ScalabilityGroups]` are restored from them at each start, so none of those is ever written. What each line held is kept in `game-settings\kept.json` (and the file as first found beside it), so a group turned off puts it back unless the game changed it since. Nothing is written while the game runs (Exo's running games or its process). Once pressed it stays on (`GameSettings.Keep`): the groups on, the lines the player has since changed in the game, each file's mark of its defaults (a profile's `Mark`: Rocket League's `[IniVersion]`, the Default*.ini write times its engine rebuilds the whole file from when they change) and the game's program with its write time are kept in `game-settings\{id}.on.json`. Each time a library game closes (and once as Exo starts) a file an update reset is written again with the groups on, the player's lines left: its mark changed, or, once the program was rewritten, every line Exo set there (two at least) left Exo's value at once; a look at start never uses up a program change, since the game may not have run it yet. `game.settings` says `again` until the game next runs, and `game.optimizedAgain` tells the page.
- Upscalers: `Services/DlssSwapService` finds DLSS / FSR 3.1 / XeSS files in a game, swaps them with backups (the first-shipped `.dlsss` and `.exo-bak`, with `.exo-written` and `.exo-stale` markers and a `.exo-upscale.json` sidecar) and restores them byte for byte. Releases are the compiled-in pins (SHA-256), each vendor's newer GitHub releases (`DlssSwapService.VendorWatch`: at most hourly, NVIDIA DLSS, AMD's FSR SDK and Intel XeSS are asked for their latest; a newer one's DLLs that a scanned game ships are fetched from its commit, checked against GitHub's size and blob hash and the vendor's signature, and kept in `dlss\vendor-releases.json`; on by default, `AutoUpdateUpscalers`) plus DLSS Swapper's archive builds (the pins only; the catalog of newer ones is Exo's, in its cache). FSR 3.1 builds are compared by their release (1.0.2.38022 is 3.1.2), not their loader's version. Every download asks upstream first and Exo's cache second (`Services/UpstreamSource`: a cache path maps to the GitHub API, raw.githubusercontent.com, a github.com release file or DLSS Swapper's host it copies; GitHub's release redirects are followed only to its release file hosts), and the bytes pass the same checks from either. Frame generation's mods (`DlssSwapService.FrameGen`) take each repo's latest release with the SHA-256 digest GitHub publishes for its file, the compiled-in pins as the cache's fallback. DLSS's three files and FSR 3.1's two share one release id, so an update sets its siblings to the same release. Exo only moves a file to the newest release (the UI offers no older one); Update all (`dlss.updateAll`) is the only bulk path. DLSS presets are part of the GPU profile. NVIDIA's NGX overlay (`NGXCore\ShowDlssIndicator`, HKLM) is changed only through an elevated `reg.exe`, so Windows prompts each time.
- Capture: Exo Capture (`capture/`, C#/.NET 10 Native AOT, MIT in `capture/LICENSE`, with the OBS game-capture hook it runs staying GPL-2.0-or-later and separate files, `capture\build.ps1`) is a separate program, shipped under `addons\capture` (or `%LOCALAPPDATA%\ExoLauncher\addons\capture`, which wins), started at `shell.prepare` by `Services/CaptureAddon` and spoken to in NDJSON over stdio (`MainWindow.Capture`, `capture.*`, events `capture.state` / `capture.saved`). It captures the running game's window (found by its process image under the game's install folder) or the screen with Windows.Graphics.Capture at the clip's rate (60, or up to 120 fps), at the lowest GPU priority. When Windows capture gets no frame from a game window for five seconds (exclusive full screen), it takes frames from inside the game with OBS Studio's own signed graphics hook (`capture\third_party\obs`, OBS's anti-cheat-compatible injection; `capture/ExoCapture/Capture/HookSource.cs` speaks OBS's hook protocol). Never for Riot games, while FACEIT or ESEA runs, for Store apps, or when another app already captures that game. It converts on the GPU (D3D11 video processor, BGRA to NV12/P010) and encodes with the GPU's Media Foundation encoder (NVENC, AMF, Quick Sync on the capturing adapter; AV1, else HEVC, else H.264, only a codec Windows can play back, stepping down when an encoder refuses to start), so frames never touch the CPU. Sound is four AAC tracks: the mix, the game (process loopback of its tree; on the desktop everything but Discord), Discord, and your microphone (Exo's Input Device, held raw in a replay and cleaned by Exo when a clip is saved); a missing source is a silent track. Instant replay keeps encoded packets in RAM from a key frame (one a second); a recording writes fragmented MP4 (`.mp4.part`) made plain on finish so a file cut short still plays. Trim is a key-frame cut without re-encoding; Discord and Vertical exports re-encode to H.264. Snips are taken by the add-on, copied at once, saved as PNG and opened in the Captures sheet's editor; on an HDR screen the frozen picture comes from desktop duplication in FP16 scRGB, tone-mapped to sRGB against Windows' SDR white. The shell reads captures from `captures.exo-launcher.local` and `capture-thumbs.exo-launcher.local`. Without the add-on the Capture button hides and Settings › Capture says Exo Capture is not installed.
- The relay (`relay/`, relay/README.md) is Exo's one server piece: a Cloudflare Worker with a Durable Object per topic that forwards opaque messages. Friends' Exo apps use it for the friend link (`docs/architecture/discord-client.md`). The Exo apps in one Discord call use it so Listen along and the Jam box can follow someone's Exo music without Discord being told it. The topic and key come from the call's own DAVE group: Exo adds `daveSessionExportSecret` (MLS's exporter, RFC 9420 §8.5) to the libdave it builds (`voice/dave-exporter.patch`, applied by `voice/build.ps1`, with its test in libdave's suite), and `DaveSession.CallSecretChanged` gives each epoch's 32 bytes, which `CallRelayFormat` expands (HKDF-SHA256) into a 128-bit topic and an AES-256-GCM key. Each join or leave is a new epoch, so a new topic and key. `CallSongs` (one per call, held by `DiscordSession.CallSongs.cs`) sends your Music room's song (fed from `MainWindow.Music.cs`'s playback) and takes the others' only from ids the voice gateway announced in the call; the page gets them as `discord.callSong` / `discord.callSongs`, Listening activities that `ui/src/lib/listenAlong.ts` prefers to Discord presence. The relay can see IP addresses, a per-epoch random topic, how many connections share it and the timing and padded size (256/512/1024/1536 bytes) of messages; it cannot see who anyone is, which call, or what plays, and it keeps each connection's last message only in that connection's attachment (no storage, no logs). A call that isn't end-to-end encrypted gets no relay. `CallRelayClient.Endpoint` is the deployed relay (none until it is deployed), or `EXO_CALL_RELAY` naming one on loopback (`relay/local/server.mjs`).
- The Exo account (`Services/Account`, `accounts.getexo.app`, source in `cloud/account`) is required for everyone: email and password, one session per PC, and the items `PlayerData.cs` marks as synced. Exo's own servers are that service, the update address, the crash and app-data service (`cloud/reports`), the cover cache (`cloud/covers`) and the relay; `NetworkDestinations.cs` lists every host native code contacts and `PRIVACY.md` has a row for each. `Services/LegacyProfileDataCleanup` runs once per start (deferred, after the shell paints) and deletes, by exact name in `%LOCALAPPDATA%\ExoLauncher` and `%APPDATA%\ExoLauncher`, what retired features left behind (for the retired older Exo account of 3.3 and 3.4, `auth.bin` (+ `.tmp`) and `online-cache`). It never contacts a service.
- GPU profile (`Services/GpuProfileService`, `gpu.profile` / `gpu.import`, PC › Graphics › Driver and profile): one NVIDIA global profile per GeForce series (GTX 10/16, RTX 20/30/40/50) . `Helpers/GpuProfile` holds every value (pure, tested); `docs/architecture/gpu-profiles.md` has each setting's verdict, reason and source. Variable refresh off, V-Sync and caps the games', Low latency On, a shader cache that never shrinks, DLSS presets (Super Resolution K and Ray Reconstruction F on RTX 20/30, NVIDIA's recommended on RTX 40/50, Frame Generation C on every RTX card), and NVIDIA's defaults back for placebo or harmful tweaks. Use Exo's profile writes every setting of the variant the driver lists to the global profile in one session, after saving every value it replaces to `gpu-profile.json`; Undo writes those back and a re-apply or variant switch keeps the first backup. Each read compares the driver with the applied variant, so a value moved by a driver update or another tool shows Re-apply. A Profile Inspector .nip (`Helpers/NvidiaProfileImport`) of the global profile is read into a plain-words preview and applied; Undo puts back what it replaced (kept until Exo closes). A Radeon gets its own profile (`Helpers/GpuProfile.Radeon`, written by `Services/RadeonProfileService` through ADLX's official Set calls in `Helpers/AmdAdlx.Settings`, backed up to `amd-profile.json` first, Undo the same), Anti-Lag always on; Fluid Motion Frames as Exo decides per game (`Helpers/FluidMotionFrames`, from `Services/FrameGenFacts`: Steam's tags and requirements, PCGamingWiki through `Services/GameWiki`, the upscaler scan; read by `gpu.game`) is set in `LaunchOrchestrator.GameLaunching` and put back once no game runs (`amd-games.json`); `gpu.sensors` reads its temperature, power, clock, VRAM and fan. When ADLX does not answer, and on Intel (`Helpers/IntelIgcl`), the page lists what to set by hand next to what the driver holds.
- Auto tune (`system.tune`, PC's chip; `Services/AutoTune.cs` decides, `AutoTune.Native.cs` is the rest; research, limits and sources in `docs/architecture/auto-tune.md`): off until pressed, never in Best settings. One press starts `ExoLauncher.exe --auto-tune` elevated (Windows asks once), which needs Exo open. It measures stock, then raises the value one step at a time with a marker on disk (`testing.json`) before each, running Exo's own load (`Helpers/TuneLoad.cs`: a Direct3D 11 compute shader, or one thread per core; each answer checked against stock's) under `TuneLimits`, watching WHEA and driver resets (`TuneEvents`), the part's temperature, a game and the battery. It settles one step short of what failed, proved by a long run. A marker found later means that value took the PC down: it fails and no search goes that deep again. GeForce: NVML's clock offset and clock lock, nothing else (`TuneNvidia`). Radeon: AMD's own tuning through ADLX (`TuneRadeon`, `AmdAdlx.Tuning.cs`). Ryzen 5000, 7000, 9000 desktops: all-core Curve Optimizer through PawnIO, which the user installs, and its signed module in `Assets/pawnio` (`TuneRyzen`); built but hidden for everyone (`AutoTuneService.RyzenAvailable` is false) until PawnIO is shown to work beside Vanguard and EAC. State, marker and script live in `%ProgramFiles%\ExoLauncher Tune`, which only the worker can write and Exo reads. What passed comes back through `apply.ps1`, a generated script of integers run as SYSTEM by the task `Exo\AutoTune` at sign-in and on wake (`TuneSignIn`): one crash at most, since it stops at a marker, a crash logged since, or its own unfinished apply. Undo and uninstalling remove it. All of it is tested against fakes only (`AutoTuneTests`).
- Drives (`system.drives`, PC › Drives; `Services/Drives.cs` decides, `Drives.Native.cs` reads): every physical disk behind a fixed volume, asked through `\\.\PhysicalDriveN` opened with no access (`PcAbout.DiskNumber`, the handle `PcAbout` already opens): the descriptor (model, bus, firmware), write cache, temperature, and on NVMe the SMART/Health log and Identify Controller through StorageDeviceProtocolSpecificProperty; on SATA the SMART data `IOCTL_STORAGE_PREDICT_FAILURE` returns. The NVMe controller's driver service and PCIe link (current against maximum) come from cfgmgr32 device properties, the flushing setting from the disk's `Device Parameters\Disk`, the optimize schedule from schtasks' XML and Automatic Maintenance's key; none needs administrator rights. The two fixes (CacheIsPowerProtected 0; the ScheduledDefrag task on, MaintenanceDisabled gone) run in one `ElevatedCommands` step with a backup in `exo-drives.json` for Undo. `Services/DriveSpace` sizes what fills each drive without a whole-drive walk: games by their store's size, Direct3D's shader caches (`D3DSCache`, each folder's small SQLite file read from a copy for the program it names, matched to a game's install folder), Steam's by app id, the drivers' caches, Exo's folder and Steam folders no manifest owns; for a game that ships dstorage.dll its biggest files get `FSCTL_MANAGE_BYPASS_IO`'s query (opened unbuffered for reading). Kept ten minutes. Old caches and Exo's old app backups are `JunkFiles` kinds (`shaders`, `exo`), deleted inside their root through no folder link. `Services/DriveHeat` samples a running game's drive every 10 s (temperature, thermal counters, link) only while a library game runs and keeps a session worth saying in `drive-heat.json` for `game.extras`. `GameInstallAsync` asks in Exo's own window before an install leaves its drive under 12% free. Exo never flashes, trims, tests or sends a drive a command.
- Network (PC › Network, `gpu/NetworkSection.tsx`): the connection Windows routes through comes from `system.about` (`PcAbout.Connection`: the Ethernet or Wi-Fi adapter that's up with a gateway, Ethernet first, no virtual switches; its kind, link speed and the adapter's name), Exo's settings for it from `system.health`'s `network` and `netlink` rows (`Services/NetworkTune`: Energy-Efficient Ethernet and Intel's DMA coalescing off, shrunk receive and transmit buffers back to the driver's own size, each only where the adapter's driver lists the value; read from the network class key without administrator rights, written in one `ElevatedCommands` step with every value backed up for Undo, the adapter restarted so its driver takes them, refused during a call or a game; an Ethernet link at 100 Mbps or less on a gigabit-or-faster adapter left to negotiate is said, not fixed). Wi-Fi has nothing to set: while a game runs `Services/WifiGameMode` stops Windows' background scans and turns on media streaming mode through the Wlan API, and on battery puts the power plan's Wi-Fi power saving to Maximum Performance, all put back when the last game closes. These rows appear nowhere else in the room; Best settings for this PC runs the same `network` action.
- System (Best settings › System, `gpu/SystemGroup.tsx`; `Services/SystemTuning` decides, `SystemTuning.Native.cs` reads; `system.tuning`; research and what was left out in `docs/architecture/system-tuning.md`): Windows defaults a tweak changed, each only where it's changed, put back by Use best settings: the forced platform clock (a 14.318 MHz performance counter; `bcdedit` `useplatformclock` removed only when the elevated step finds it), Win32PrioritySeparation with fixed quanta or no foreground boost (back to 2), no page file (back to `?:\pagefile.sys`), LargeSystemCache 1 (back to 0). Two opt-ins, only by their own switch: Downloaded Maps Manager and Program Compatibility Assistant from Automatic to Manual, and Memory Integrity off (asks twice; refused beside Riot Vanguard or FACEIT, under the Device Guard policy or its UEFI lock). Every value is a constant in code, recorded in `exo-system-tuning.json` before one elevated step (`ReplacedApps.RemoveAsAdminAsync`) that makes a restore point first (`RestorePoint.Step`), read back after, and put back exactly by Off; a change waits on a restart and says so. Nothing needs TrustedInstaller.
- Settings is one sheet with a sidebar, the rooms' pages first and then Exo's own, a hairline between them: Library (game stores and keys, Downloads, Achievements, FPS counter), Discord (six pages of Exo's own, each drawn alone: Voice and video, Chat, Notifications, Privacy, Account, Keys and advanced), Music, General, About (`ui/src/components/SettingsPanel.tsx`, `ui/src/lib/settingsSections.ts`). Discord's settings live only there; the Discord room links to them and has no gear of its own.
- One layout on every screen: `MainWindow.PageScale` lays the page out as on a 1080p screen, either way up, and draws it larger on a bigger one (`Helpers/PageScale`; `EXO_PAGE_SCREEN=1440` or `=1080x1920` tries another screen's zoom).

`MainWindow` is the only window XAML (`App.xaml` and the `Styles/` dictionaries aside); sign-in and connected-app windows are built in code. `ExoLauncher/Ui/` holds two small host helpers (`CaptionDragRegions`, `ExoUrlLaunch`), not a second room system. Do not rebuild native rooms when changing the React UI.

`hostMock.ts` loads only during development and tests. Protocol v1 method names and update-result types are checked against native source by `npm run contracts`; intentional changes regenerate `ui/contracts/host-v1.json` and `hostWire.ts` with `npm run contracts:write`. `npm run dead` runs knip in default and production mode (`knip.production.json`), so a file or export reachable only from tests fails the gate. `npm run css:prune` reports stylesheet blocks whose classes no component uses. `tools/find-dead-types.ps1` lists host types with no references outside their declaration. Cache lifetimes are in [docs/CACHE_POLICY.md](docs/CACHE_POLICY.md).

`npm run build` in `ui` emits into `ExoLauncher/wwwroot`; the project build runs it (`ui/scripts/build-cache.mjs`, only when its inputs or outputs changed) before collecting web assets. The shipped app runs from `%LOCALAPPDATA%\ExoLauncher\app`. Validate in the installed app after deployment.
