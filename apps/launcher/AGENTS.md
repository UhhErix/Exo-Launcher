# Exo Launcher — working rules

Exo is a Windows 11 launcher: one UI over the official store clients, which stay installed where the vendor put them and become invisible backends. Rooms (native, `native-ui/crates/exo-ui/src/state.rs`): Library, Store (Steam-ranked shelves, official stores, wishlist), Discord (Exo's own client; its first place is Home), Music (Spotify, Apple Music and YouTube Music, each its own web player), Devices (mouse, audio, controller), Exo AI (this PC: graphics, display, board, storage, Auto tune, Exo Shaders), Apps (apps and game runtimes). Settings is the gear and its own room. Classic React still has PC in place of Exo AI and Apps. `CONTEXT.md` has the domain, `ARCHITECTURE.md` the shape, `DESIGN.md` the look. Read the one you need, not all three.

## Hard stops

- Never fake store replacement, edit game binaries, or touch anti-cheat (the one exception: the user may take Vanguard's tray icon, vgtray, out of startup and put it back; vgc and vgk are never touched). Never kill anti-cheat (Vanguard, EAC, BattlEye, FACEIT, PunkBuster, XIGNCODE, GameGuard, ACE, a game's `_BE`/`_EAC` launcher), at the root or anywhere in a tree. Exo never changes Riot's games or Vanguard's driver and service. It may hide and close the Riot Client's windows, ask it to quit, switch its signed-in account, and, if you choose, take Vanguard's tray icon out of start-up. Nothing is injected into or placed in a game with anti-cheat, and a game whose anti-cheat Exo cannot read counts as having it (`Services/AntiCheatCheck.cs` is the one answer every place asks); the only change allowed there is the vendor's own signed upscaler file, swapped for a newer one with the player's consent for that game. The one exception for frame generation and mods: a Steam game the player starts from a Steam launch entry that runs without its anti-cheat (Properties › Anti-cheat), and then only for a session Exo starts: they go in at Exo's Play and are taken out once the game exits (`Services/DlssSwapService.SessionMods.cs`).
- Steam install/update/uninstall goes through `ExoLauncher.SteamIpc`. Epic = Legendary, GOG = gogdl. Documented exception: the Steam Beta switch (writes `package\beta`, then closes Steam with its own `-shutdown` and starts it again) runs in Exo's own code (`WebHostBridge.Clients.cs`, `SteamBetaFile`) for Game clients' Fix, and puts the old branch file back on any exit that does not reach Beta. No OCR, DepotDownloader or CDN scraping. Commands, progress parsing and Steam helper internals: `docs/architecture/vendors.md`.
- Exo asks the player before any download, install or elevated action. No ads, tray agents or third-party analytics. Exo's own app telemetry and crash reports are sent by every install, with no switch (`docs/decisions/2026-11-09-telemetry-always-on.md`): they stay anonymous (a random install ID, schema-checked and scrubbed on the PC, never an account, a name or hardware), PRIVACY.md lists exactly what is sent, and Settings › About (Privacy) keeps What's sent and Delete my data. Exo's own notification-area icon is allowed: it exists only while Exo runs, keeps nothing running, and starts with Windows only when the player turns on Settings › General › Open Exo when Windows starts (one HKCU Run value, off by default).
- Secrets and filesystem paths stay in the host. The UI (exo-ui or classic React) gets bounded DTOs.
- Never drive VALORANT, League or another anti-cheat game from an agent session: scripted input there can get the account banned.
- No emoji in chrome.

## Stack (4.0.0)

The native Rune UI is the default (`docs/decisions/2026-11-20-native-ui-rune.md`): `native-ui/` builds `exo-ui.exe` (Rust, wgpu DX12, our Rune fork `UhhErix/rune` pinned to `be38cbbc` in `native-ui/Cargo.toml`). The .NET host spawns it (`Services/RuneHostSession.cs`) and talks to it over `IHostTransport` named pipes (`NamedPipeHostTransport`) with the `host-v1.json` contract; WebView2 stays in the host for pages that cannot leave a browser. New UI work lands in `native-ui/`.

Classic React is the fallback: `--ui=web`, `EXO_UI=web`, the `useClassicWebUi` setting, or no `exo-ui.exe` beside the host. Known issue: `TrimUnusedPublishFiles` in `ExoLauncher.csproj` deletes the React bundle from `wwwroot` when `exo-ui.exe` is published, so the classic fallback is likely broken in an installed 4.0.

Classic: WinUI 3 + Windows App SDK 2 + .NET 10 host (stable only; .NET 11 waits on `docs/RUNTIME_RELEASE_READINESS.md`), one WebView2, React 19 + Tailwind 4 + Lucide icons (named for Exo in `ui/scripts/lucide-map.mjs`, used through `ui/src/brand/icons.tsx`, data written by `npm run icons`) in `ui/`, with native controls in `ui/src/components/ui/` (no component library). `WebHostBridge.cs` dispatches JSON-RPC named in `ui/src/lib/host.ts`; the manifest is `ui/contracts/host-v1.json`. Windows 11 x64 only.

## How to work

1. **Evidence before opinion.** Screenshot the running app, read `%LOCALAPPDATA%\ExoLauncher\logs\app.log`, run the analyzers. `tools/e2e` drives only the classic UI. The native UI is driven over UI Automation by automation ids (Rune keys): `tools/rpc-parity/uia.ps1`, `tools/rpc-parity/run.mjs` (host calls, native against classic) and `tools/parity` (screens, native against classic). Do not diagnose from memory of the code.
2. **Size it, say it.** One line before starting: `small | medium | large — why`. Small (copy, one-file fix): touch it, build, ship. Large (contract, cross-layer, design): plan first, then build.
3. **Deterministic work is a script.** Counting, diffing, dead-code detection, contract checks, CSS pruning: write or run the tool, never reason it out. The tools that exist: `npm run dead`, `npm run css:prune`, `npm run contracts`, `tools/find-dead-types.ps1`, `tools/rpc-parity`, `tools/parity`.
4. **Delete, don't flag.** If it is not reachable in the shipped app, remove it: the code, its CSS, its RPC, its mock, its doc line. No feature flags for retired code, no "keep for later".
5. **Simplest thing that is correct.** No new abstraction until the third caller. Inline one-branch wrappers. Prefer a hairline to a card, a row to a dropdown, a constant to a setting nobody can change.
6. **Fix the cause.** A misleading label is renamed to what it does. An error the user waited on reaches them as one status line and reaches `app.log` via `report()`/`AppLog`.
7. **Verify on the real thing.** A clean build is not done. Done is the installed exe running the change with the room on screen. A cloud session cannot get there: Devin's Windows VMs are Windows Server 2022 (build 20348) and Exo refuses to start below build 22000 (`Helpers/WindowsRequirement.cs`), so neither the installed app nor `tools/e2e` runs. There, run the Gates and `dotnet test`, check a classic visual change on the mock host (`npm run dev`, `webapp-testing`, `npm run crawl`; a native visual change can't be checked there), mark the CHANGELOG entry `_Checked in code only._`, and list in the PR what still needs a look in the installed app on Windows 11.

A WebView (CDP) screenshot shows only Exo's own page, and it can look whole while the screen doesn't (3.13.3's 4K page did): the E2E suite compares a capture of the screen itself with the page (`screenMatchesPage`). Every embedded client session is Exo's: the music service you chose starts hidden with its room, and it closes with Exo, on a provider switch, or after 15 minutes asleep. Exo AI's shader board hosts no window: it is Exo Shaders, a headless engine (`Services/ShadersAddon`) driven by Exo's own board (`exo-ui/src/pc_ai.rs`; classic `ui/src/components/shaders/ShadersBoard.tsx`).

Native Devices draws Mouse, Audio and Controller in Rust (`devices_mouse.rs`, `devices_audio.rs`, `devices_controller.rs`). Classic Devices is Exo Mouse, a separate AGPL-3.0-or-later program in `mouse/` built on `@openmouse/protocol`, vendored in `mouse/vendor/openmouse-protocol` (0.60.0-exo.1; Exo's changes in `mouse/vendor/exo-patches`). It runs in an iframe on its own origin (mouse.exo-launcher.local) and talks to Exo only by postMessage; `ui/src/lib/mouseRelay.ts` relays HID calls and events, the installed games (id, title, cover thumbnail), its saved profiles, game start/stop, Exo's text size, motion and its look (CSS values read off Exo's own surfaces, never code or a style sheet), and the mouse's CPU core (`exo.mouseCore`: a read or one of three actions, run by the host), and nothing else; `DevicesRoom.tsx` frames it. Never put Exo code into `mouse/` or AGPL code into `ui/`; Exo Launcher is not under the AGPL. Run `npm ci` in `mouse/` as well as `ui/`. `mouse/scripts/build-protocol.mjs` builds the vendored library before `check` and `build`. The AGPL obliges its source to be public: any release publishes `mouse/`'s source at getexo.app/source first: `node cloud\updates\addon-source.mjs build` makes `exo-mouse-<version>.tar.gz` from the committed tree (no `node_modules`/`dist`; it builds standalone into `dist/`) and `addon-source.mjs upload --dir artifacts\source` puts it, with the index, in R2 `exo-source`. Exo Shaders is the same: a separate GPL-3.0-or-later program (with SCSKiller's section 7 exception) in `shaders/`, Exo's fork of SCSKiller, run as its own process (`ExoShaders.Service.exe`, NDJSON over stdio, `shaders/engine/CONTRACT.md`); never put Exo code into `shaders/` or GPL code into `ExoLauncher/` or `ui/`. The fork is ours: improve it freely (engine logic, game support, reliability, speed), keep the SCSKiller authors' copyright notices beside ours, and keep upstream mergeable while that is cheap: a source copy, not a submodule, our changes in clean commits that say what they change, and `shaders/UPSTREAM.md` recording the upstream commit and how to take a new release; diverge only where ours is clearly better. `tools/Build-Release.ps1` builds it from the committed tree (`tools/Build-ShadersEngine.ps1` refuses uncommitted changes) and the same `addon-source.mjs build --launcher <apps/launcher> --rev <commit>` publishes `exo-shaders-<version>.tar.gz` from that commit. Exo Shield (the extension folder in `ExoLauncher\Assets\Extensions\exo-shield`) is in the same archive set, OBS Studio's hook source comes from `addon-source.mjs fetch-obs`, and all go up in one `upload` before the release. Exo Capture (`capture/`) is MIT licensed (`capture/LICENSE`), while its bundled OBS Studio game capture binaries in `capture/third_party/obs/` remain GPL-2.0-or-later (`capture/third_party/obs/README.md`).

Switching music providers closes the previous page; leaving Music for another room only hides it. Exo never starts, hosts, installs or prompts for the Spotify app; one the user runs is closed (then ended if it stays in the tray) when Exo starts Spotify's player, because it keeps the player from loading (`Helpers/SpotifyApp.cs`).

Code style: the smallest complete change, reuse before adding, delete what a change replaces (never leave it flagged). Review a diff against How to work 3 to 6 and the Enforced rules table. Reverse engineering: the REA MCP (`rea`) or plain CLI tools. A client's settings or config file can hold account names and tokens, so read it only on the PC it came from and never paste it into a commit, PR, log or another agent's task.

## Design

One look: Void black `#000` for the page and its panels, every color a token (DESIGN.md › Tokens). Type: native exo-ui embeds Geist (`exo-kit/assets/fonts`); classic, the installer and the host's own surfaces use Goeist, Shadcn Labs' rounded Geist (`ui/public/fonts`, `ExoLauncher/Assets/Fonts/Goeist-Variable.ttf`). Which font native should draw is an open decision. Icons: Keyline in native (`exo-kit/src/icons.rs`), Lucide in classic. One Bar of capsules; in native it hides as the page scrolls (`shell.rs`). Liquid Glass is on what floats and on the controls (`docs/decisions/2026-11-14-liquid-glass-back.md`): each glass blurs what is behind it and nothing else. A control is clear glass with its hairline, a label over art sits on glass with a deeper dim, and what floats (menus, sheets, Ctrl+K, toasts, the player) is black glass over the frost. Rows repeated down a scrolling list take no backdrop. Native glass is `exo-kit/src/glass.rs`; classic classes say `exo-glass` and `ui/src/styles/glass.css` opens with what it does. Classic legibility is measured from the screen's pixels by the E2E `rooms` and `appearance` suites (words under 3:1 fail, under 4.5:1 warn). Structure by hairlines and a shared right-aligned control column, not nested cards. Sentence case everywhere; no tracked capitals. Section names are the only bold type. Fill the window; a page that fits without scrolling does not get a sidebar or a disclosure. Discord is Exo's own client (`ui/src/components/discord/`, `Services/DiscordClient/`); Exo never hosts or patches the Discord app. Music for Spotify, YouTube Music and Apple Music is Exo's own player (`ui/src/components/music/`, one adapter per service in `ui/src/lib/musicAdapters.ts`): the service runs hidden as the engine and Exo draws home, search, library, pages, queue, lyrics, and for Spotify devices, Jam and Friend activity, through the service's own APIs (`Helpers/SpotifyNative.cs`, `Helpers/YouTubeMusicNative.cs`, `Helpers/AppleMusicNative.cs`: music.apple.com's own MusicKit instance, never its tokens); its own UI shows only to sign in. Exo always optimizes a hosted page (no setting): it declutters YouTube Music. Full tokens in `DESIGN.md`.

Skills: project skills in `.agents/skills/` (`native-ui`, `exo-design`, `frontend-design`, `impeccable`, `web-design-guidelines`, `webapp-testing`, `delete-comment`; provenance in `SOURCES.md`), user skills in `~/.config/opencode/skills/`. Use `native-ui` and `rust-skills` (`unsafe-rust-review` for `unsafe`) for `native-ui/`, `vercel-react-best-practices` for classic React, `winui-development` and the `csharp-*` / `dotnet-*` skills for the host, `cloudflare-workers` for Workers, `reverse-engineer-anything` with REA, `systematic-debugging` for bugs, `impeccable` / `emil-design-eng` with `DESIGN.md` for UI, and `verification-before-completion` before claiming completion. Building or changing anything visual: `exo-design` first (Exo's rules, checks and checklist), then `frontend-design`, with DESIGN.md as the brief. Reviewing UI: `web-design-guidelines` and `impeccable` (its detector: `npx impeccable detect <files>` on the CSS you touched; not a repo script). Scripted rendered checks of the browser build (`npm run dev`, the mock host): `webapp-testing`; the installed app is checked on screen, by `tools/e2e` (classic) and `tools/parity` (native).

## Gates

From `ui/`: `npm run check` (the type check `tsc -p tsconfig.app.json`; `contracts`: every method the page calls (a name chosen by `a ? 'x' : 'y'` included) is an arm of the bridge's dispatcher with a handler that does something (an arm that only answers yes counts only when `STUB_ARMS` lists it with a reason), every typed event has a real sender, and event fields agree on both sides where both spell the payload out (68 of 83 today; a payload built elsewhere is not compared); ESLint; `lint:css`: the CSS design check, with colours from tokens only, and the icons check; dead CSS; the `test/` suite, which includes the raw-HTML sink scan `test/scanSinks.test.ts`; the comment ratchet), `npm run dead`, `npm run build` (builds `mouse/` too). From `mouse/`: `npm run check` (tsc, ESLint, CSS design check, tests), `npm run build`. Intentional RPC changes: `npm run contracts:write`. Before a release, from `ui/`: `npm run crawl` (`tools/ui-pass/crawl.mjs`: every room and state on the mock host in headless Chromium; exceptions, console errors, failed requests, sideways scroll, words past the window, contrast under 3:1 and error screens fail it; it needs Playwright's Chromium, so it is not part of `check`).

## Testing

- `ExoLauncher.Tests` (xUnit) is for pure logic whose failure is silent in the app: parsers, process ownership, update and network policy. Each test class opens with the ways the code could fail.
- Highly prefer E2E tests as the sole testing mechanism. Use them to verify complex features work. At the end of E2E tests, produce a verifiable and repeatable artifact.
- If you must test a system in isolation, first write down all the ways it could fail, then write the code.
- The E2E run is `node tools\e2e\run.mjs` (Node 22+, PowerShell 7, no packages; tools/e2e/README.md has the suites, flags and report). It drives the classic UI over CDP only; native rooms are checked with `tools/parity` and `tools/rpc-parity` over UI Automation. It refuses to start during a Discord call or a game, saves the files it may touch, closes Exo normally and restarts it with a loopback-only CDP port in the child's environment, and drives the real UI with real input. It checks what the screen itself shows (not only the page's own picture), measures contrast from pixels, times frames, room changes, scrolling, memory and idle CPU, stresses rooms, sheets, menus and window sizes, and restarts Exo as on a 1440p and a 4K screen; then it puts the files back byte for byte and starts Exo again. It never kills a process, buys, installs, plays sound or posts anywhere but the Discord test place (its message is always deleted). Real mouse clicks and window moves stay on Exo's own window: keep hands off while `shell`, `stress` and `zoom` run.
- The artifact is `e2e-reports/<yyyyMMdd-HHmmss>/` (gitignored): `summary.md`, `report.json` (every check with status, timing, numbers, evidence and screenshots, personal identifiers masked), `screenshots/` and `SHA256SUMS.txt` (`sha256sum -c`). Exit code 1 means a check failed; a FAIL must be an app bug, so fix the check if it is not. New features add their check to the suite they belong to.

## Ship

Iteration only: `pwsh -File Run-ExoLauncher.ps1` (Debug; it doesn't build `exo-ui`, so run `cargo build --release --locked --bin exo-ui` in `native-ui/` first or it falls back to classic). For hot reload, run `npm run dev` in `ui/` and start the Debug build with `EXO_UI_DEV_URL=http://localhost:5174`.
Shipping: delete the Release `win-x64\publish` and `win-x64\R2R` folders under `ExoLauncher\bin` and `ExoLauncher\obj` first (an incremental publish once shipped plain IL instead of ReadyToRun; the E2E `shell.precompiled` check catches it), build `exo-ui` (`cargo build --release --locked --bin exo-ui` in `native-ui/`; the publish copies `native-ui\target\release\exo-ui.exe`), then `dotnet publish` (Release, x64, self-contained), then `pwsh -File tools\swap-dev.ps1` (stages into a unique `app.incoming-dev-*`, closes Exo normally, and swaps over `app` while retaining a unique `app.previous-dev-*` backup; never force-kills), launch `%LOCALAPPDATA%\ExoLauncher\app\ExoLauncher.exe`, then run `node tools\e2e\run.mjs` (`shell.log-clean` checks `app.log` for errors and `shell.precompiled` the ReadyToRun build, among everything else). Never run it while the user is in a game; it restarts Exo and drives the window. Memory: `pwsh -File tools\measure-memory.ps1` on the installed exe, 3 minutes after launch, sitting on Library. Releasing is publishing a stable GitHub release with the installer, its `.sha256` and `whats-new.json` attached: the exo-updates Worker reads it from GitHub itself, writes it into the update mirror (R2 `exo-releases`), copies the installer into R2 with its SHA-256 checked, and posts the Discord release card once (root `RELEASES.md`, `cloud/updates/README.md`). There is no upload step for the launcher; `cloud\updates\publish-release.ps1` stays for Exo Cinema (and can still put a launcher build into the mirror by hand). Help links point to getexo.app/help.
CHANGELOG entry under the current version, in product voice. Every entry ends with how it was checked, in italics: `_Verified: on screen._` (seen working in the installed app), `_Verified: end-to-end._` (a `tools/e2e` check covers it), or `_Checked in code only._` (anything not seen on this PC: other stores, services, hardware, sign-in flows).
