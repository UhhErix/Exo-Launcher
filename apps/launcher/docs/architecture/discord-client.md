# Exo's own Discord client

The Discord room (id `friends`) is Exo's Discord client (`ExoLauncher/Services/DiscordClient/`, `ui/src/components/discord/`); Exo never hosts, installs or patches the Discord desktop app. It covers text (servers, channels, threads, forums, DMs, messages, reactions, pins, polls, search, inbox), server settings and moderation, Discord's settings, calls, cameras and Go Live. Video and Go Live: `discord-video.md`.

## Rules it keeps

- Signs in only by QR code (Discord's phone app confirms); Exo never takes a password.
- The token is DPAPI-wrapped in `discord-client.bin` (current user only, `DiscordToken`), sent only to Discord's own hosts, never to the UI, never logged. Sign out deletes the file and calls `POST /auth/logout`.
- Acts only on what the user does in the room (and, once they turn Share my games on, says which game they opened from Exo). No automation, nothing on a timer for anyone else, no captcha solving: a captcha reply becomes a plain line telling the user to use the Discord app once.
- Channel visibility is computed in the host (`DiscordCache`) with Discord's permission rules: base from @everyone plus the user's roles, Administrator or owner sees all, then the channel's @everyone, role and member overwrites. A channel without View Channel never reaches the UI, nor do its messages or typing (`DiscordCacheTests`). No deleted-message logging: a delete removes the message.
- Messages are held only in memory (the page keeps the newest of the last 30 conversations, `messageCache.ts`); nothing is written to disk.
- No Nitro entitlement spoofing.

## Protocol (as Discord's web client)

- Identity: Chrome on Windows (`DiscordRest.Properties`), the User-Agent from the installed WebView2's major version, and `client_build_number` read from discord.com's own scripts at start (fallback constant).
- QR sign-in (`DiscordRemoteAuth`): `wss://remote-auth-gateway.discord.gg/?v=2`. Exo sends `init` with an RSA-2048 SPKI key, answers `nonce_proof` with base64url(SHA-256(decrypted nonce)), shows `https://discord.com/ra/<fingerprint>`, then trades the `pending_login` ticket at `POST /users/@me/remote-auth/login` for `encrypted_token` (RSA-OAEP SHA-256). The key exists only for that sign-in.
- Gateway (`DiscordSession`): `wss://gateway.discord.gg/?encoding=json&v=9`, no compression, capabilities `DEDUPE_USER_OBJECTS` (1<<4) so READY carries `users`, `recipient_ids` and `merged_members`. Heartbeat, zombie detection (no ACK means reconnect), resume through `resume_gateway_url`, a fresh identify after op 9 with `d: false` or close 4007/4009, sign-out on 4004. Opening a server channel sends op 37 (bulk guild subscriptions) for live messages in large servers; if the gateway answers with 4002 right after, Exo stops sending it.
- REST (`DiscordRest`): `discord.com/api/v9` for messages (50 per page), send (`nonce` snowflake, `message_reference` for replies), edit, delete, ack (`last_viewed` as days since 2015-01-01) and typing. 429s under 10 s are waited out up to twice.
- Notifications (`DiscordCache.Notifies`, after the web client's `shouldNotify`): never your own message, a `SUPPRESS_NOTIFICATIONS` (@silent) one, a blocked person's, a message request's, or anything under Do Not Disturb, and each message once. DMs notify of every message unless muted; servers follow mutes (server, category, channel, a thread's channel), opt-in channels and the resolved level, with a voice channel's chat at All Messages only while in that call. `DiscordNotifier.Route`: nothing for the conversation on screen while Exo is in front, nothing while a game runs with Game focus on; only the sound under Streamer Mode's Disable notifications or with desktop notifications off; else Exo's banner (`discord.notify`) while in front, a Windows notification (tag = message id, group = channel id, the avatar as a local PNG) in the background. MESSAGE_ACK, a local ack, opening the conversation and Exo coming to the front clear the channel (`discord.notifyClear` and `RemoveByGroupAsync`), as Discord does on MESSAGE_ACK, CHANNEL_SELECT and WINDOW_FOCUS; MESSAGE_DELETE removes that one message's.

## Voice

- Joining (`DiscordSession.Voice.cs`): main gateway op 4 `{guild_id, channel_id, self_mute, self_deaf, self_video, flags: 2}`; Discord answers `VOICE_STATE_UPDATE` (this session's voice `session_id`) and `VOICE_SERVER_UPDATE` (`token`, `endpoint`; for a DM call `channel_id` stands in for the guild). DM calls ring with `POST /channels/{id}/call/ring`; `CALL_CREATE` or `CALL_UPDATE` ringing this user notifies.
- Voice gateway v8 (`Voice/VoiceConnection.cs`): identify with `max_dave_protocol_version` from libdave, heartbeats `{t, seq_ack}`, resume `{server_id, session_id, token, seq_ack}`, binary DAVE messages. Closes 4004, 4011, 4014, 4016, 4017, 4021 and 4022 end the call; 4006/4009 start over.
- UDP (`Voice/VoiceTransport.cs`): IP discovery, then RTP (payload type 120, Opus 48 kHz stereo, 20 ms) under `aead_aes256_gcm_rtpsize` (preferred) or `aead_xchacha20_poly1305_rtpsize`. The RTP header and extension preamble are the additional data; a big-endian 32-bit counter is appended as the nonce.
- DAVE (`Voice/DaveSession.cs`): a C# port of libdave's reference `DaveSessionManager` over its C API (`dave.dll`, `Voice/VoiceNative.cs`); only users announced by op 11 are accepted into the MLS group.
- Sound (`Voice/VoiceAudio.cs`): shared-mode WASAPI on the chosen devices, else Windows' default microphone and speakers (`AudioDevices`, the console role, as Discord picks them), event driven, Windows converting to 48 kHz stereo float. Microphone sound more than 40 ms later than that mic usually is gets dropped, not sent late. Five Opus silence frames before speaking stops. Each speaker is evened out toward one speaking level (`VoiceLeveling`, Even Out Voices) and gets a jitter buffer that starts at 60 ms and drops past 200 ms. `Voice/LiveAudio.cs` keeps Exo fit for real time while any live sound runs, and each audio thread joins MMCSS as it starts (`MmcssTask`).
- Microphone chain (`Voice/VoiceChain.cs`, the same for a call, Voice Check and Voice Tune): echo cancellation on speakers first (`Voice/EchoCanceller.cs`, WebRTC AEC3 in `exo_apm.dll`), then the low cut and knock detector, noise suppression, Voice Focus or the level gate (`Voice/VoiceFocus.cs`, `VoiceGate`), gain control on the cleaned voice (`SpeechLeveler`), the gate's release fade, the compressor (`Compressor`), then Clip Guard. Profiles: `Voice/VoiceInput.cs`; per-mic tuning: `Voice/VoiceTune.cs`.
- Your voice in captures (`Voice/RecordedVoice.cs`): a recording, written as it goes, runs a chain of its own (`VoiceChain.Recording`) and feeds Exo Capture's microphone track live; a call feeds it from the call's chain, whose cost is already paid. A replay only being kept runs nothing of Exo's: the add-on holds the chosen microphone raw and `ClipVoice` cleans a saved clip's voice in one go, below normal priority, and the add-on makes the clip's mic track and mix again (`capture/README.md`, A clip's voice). The time-critical voice thread (`MmcssTask`) is for what has a 20 ms deadline: calls, Voice Check, Voice Tune, the meter, and a recording's chain, whose hand-over from the mic's thread holds 80 ms.
- Noise suppression (`Voice/NoiseSuppressor.cs`): DeepFilterNet 3's low-latency model through its own C interface, Exo's build of v0.5.6 with three entry points added (`voice/deepfilter/exo-capi.rs`), each 20 ms frame cleaned as two 10 ms hops on the caller's thread. Fetched once from Exo's GitHub release (pinned size and SHA-256) when the Discord client starts. Noise Suppression for Others gives each voice heard its own instance (`Voice/InboundCleaner.cs`).
- Natives: `voice\build.ps1` builds `dave.dll` (libdave pinned by tag and commit, mlspp and OpenSSL static, Visual Studio's vcpkg in manifest mode, OpenSSL 3.5 from Exo's overlay port `voice\ports\openssl`), `opus.dll` (Xiph's tag, static runtime, `voice\opus-downmix.patch`), `exo_apm.dll` (webrtc-audio-processing 2.1) and the DeepFilterNet library (needs Rust), into `voice\out`.

## Share my games and the friend link

`DiscordSession.Games.cs` says what you play; `DiscordSession.FriendLinks.cs`, `FriendLinks.cs`, `FriendLinkFormat.cs` and `FriendLinkKeys.cs` are the link. The link is a general sealed channel between two friends' Exo apps over Exo's relay (`relay/README.md`): what exists only for other Exo users goes there and never through Discord. The relay is unchanged; no Discord token, application or OAuth is involved.

- **Finding each other:** each Discord account on a PC has a P-256 key (DPAPI, `friend-link-<id>.bin`; Sign out deletes it). Its public half, compressed and base64url (44 characters), goes in the account's own presence as `party.id` on a `type: 4` activity, the real custom status if there is one (`FriendKeyCarrier`, the one place to change the carrier). Discord authenticates presence, so nobody can put a key in a friend's.
- **Pairing:** ECDH, then HKDF-SHA256 with both ids and both public keys in the info, so both sides derive one topic and AES-256-GCM key, and someone showing a friend's key gets another topic. `DiscordCache.LinkPeers` picks actual friends (relationship 1, not ignored) who are online and show a key.
- **Cap:** `FriendLinks.MaxLinks`, 16. Links up stay; new places go to whoever you last messaged. Only friends with a key connect, so most people have a few links at most.
- **Message:** one fixed size (1536 bytes plain, 1565 sealed), `{ v, at, hello?, s: { type: section } }`, the sender's whole state, since the relay holds only each connection's last message. **To add something:** `links.Set("type", value)` to send and read `message.Sections["type"]` with its own bounds; nothing in the pairing or crypto changes, an Exo that doesn't know a type ignores it, and PRIVACY.md gets the new item. Tell the owner first: each new type tells friends something new, and none is on by default without their word.
- **Replay:** the additional data holds topic and sender direction; `Receipt` refuses anything older than the last taken, or more than 10 minutes from this PC's clock. So a relay's held message can be too old to take; a client that connects sends `hello`, answered with a fresh message only when the last one sent is over 5 minutes old, and an answer asks for nothing back.
- **Grace:** a connection that ends leaves what was heard for 30 s. A friend who goes offline or loses their key goes at once.
- **Cost:** nothing polls. Each socket pings every 25 s; everything else is an event. Friend links are worked out once a moment after a key, a friend, someone's online state or your status changes (`TakeLinkPeersChanged`).
- **Source of a game:** `LaunchOrchestrator.GameLaunched` (fires only for a launch from Exo), not `GameRunStateChanged` (which also fires for a game started from its store). `GameRunStateChanged` and `GameSessionCompleted` only end it, after a 10 s grace for a launcher handing over. Only events: nothing looks at a game's process, window or files, so anti-cheat and Riot games are touched by nothing here.
- **Gates** (`LinksAllowed`, all must hold): Discord connected (no switch since 3.26.0, owner: always on; the old lists `DiscordGamesShared`, `DiscordReadyShared` and 3.22.0's `DiscordShareGames` are read by nothing and dropped on the next save), not invisible, a relay set, and Discord hasn't refused the key this run. Any shut: no key in the presence, no connection, nothing sent or heard. `MayShare` keeps out hidden games and `StoreKind.Local` titles.
- **Share my activity:** Exo no longer touches `showCurrentGame`: not forced off on connect, not turned on or off by the switch, whatever it was left at stays.
- **On the page:** a friend's game merges into their presence (`DiscordCache.WithExoGame`) as a Playing `rich` with `throughExo`, so `playingName`, `playsThroughExo` and Home read it as before.

### Share when I'm getting ready (the `prep` section)

The link's second type, said under a friend's name in the friends list (`ActivityLine.tsx`): `{ title, kind: installing | compiling | ready, pct? }`. `FriendPrep` writes and reads it with its bounds (a title of at most 128 characters, no controls or bidi, cut to 400 bytes as written so two titles always fit the link's one fixed-size message, `pct` only on an install, 0 to 100 in tens, anything else drops the whole section), `DiscordPrep` is what this Exo says (compiling before installing before ready, the latest of each; a percent only moves a step of ten; "ready" goes after 30 minutes or when the game launches; a game Share my games may not name is never tracked), `DiscordSession.Prep.cs` feeds it from `LaunchOrchestrator.ProgressChanged`, `ShaderPrepare.Changed` and `GameLaunched`, and `DiscordCache.SetExoPrep` holds a friend's. It reaches the page as `prep` on the friend and on `discord.presence`. Source of a compile: Prepare only; Exo Shaders' queue is not read. **Gate:** none of its own since 3.26.0 (owner: always on); it rides the link and its gates.

### The carrier: what is known, and what isn't

Read from Discord's web client (the bundle at discord.com/app, November 2026) and docs.discord.food; nothing was sent from any account.

- **Shown:** nothing. `ActivityStatus` treats a custom status with no text and no emoji as none (`null==state && null==emoji ? null`); `u9` returns null for it and moves on to the next activity; `isRichActivity` excludes `CUSTOM_STATUS` even with a `party`, so no Ask to Join or party UI comes of it. Your own client ignores remote custom statuses (`SelfPresenceStore`).
- **Small effect:** the member list's row sees an activity and renders an empty element where it would render none, and its subtext's `:empty { display: none }` no longer applies, so such a row's name may sit up to 2 px off. No text or icon. Not checked on screen; mobile apps' code wasn't read.
- **Share my activity off:** Discord's own client sends `type: 4` whatever the setting says (the filter `G` passes activities with no `application_id`), and real custom statuses show with it off. docs.discord.food says activities are hidden with it off, with exceptions, and that hidden ones arrive as `hidden_activities`, in sessions and in friends' presence, so `FriendKeyCarrier.Read` looks in both. Exo kept this setting off for most accounts, so this case is the usual one.
- **Stripped or not:** unknown. Nothing public says whether the server keeps `party` on `type: 4`; `party.id` is documented up to 128 characters. Discord's client does send `details` and `metadata` on it. It can only be seen on a real account: `app.log` says `Share my games: key in presence: yes`, or `no` with the fields that came back, from `SESSIONS_REPLACE`. A friend seeing it is a second question: `Share my games: N friends show a key; M linked.` and `heard from a friend's Exo`.
- **Refused:** if Discord closes the connection (4000, 4002) within 5 s of a key, the key isn't sent again that run (`KeyRefused`), so it costs one reconnect at most.
- **Next carriers, in order, if `party.id` is stripped:** `sync_id`, then `assets.small_text`, on the same activity; the log's field list says which survive. Not `state` or `emoji` (shown), `secrets` and `metadata` (send-only), `buttons` (shown), or any message or DM.
